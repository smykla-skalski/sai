# Orchestrating an approved plan

Use this workflow when Ship It receives an explicitly approved complex plan or a GitHub umbrella issue with native implementation subissues. A single implementation issue remains one worker's change. Plan approval is required to derive or create an issue graph from a plan; an existing umbrella supplies its own graph. A draft plan does not authorize issue creation or implementation. The parent coordinates and never edits product source, commits, reviews, tests or merges a child's implementation itself in any harness.

Create or resume the umbrella's durable checkpoint before building or dispatching its graph. Set `phase` to `orchestrate`, set `orchestration` to an object, and keep one child record per native subissue. Reconcile every recorded child with GitHub and its worker or worktree before resuming; never recreate a worker or repeat a completed gate from checkpoint state alone.

## Build or reuse the issue graph

1. Read the complete approved plan and its acceptance criteria, or the existing umbrella and native subissues. Resolve the target repository and search open issues for the same umbrella before creating one. Prefer an explicitly supplied umbrella; reuse a matching existing umbrella and its subissues. Do not adopt an unrelated issue based on a similar title.
2. Split the plan into the smallest independently shippable changes. Each child must have a concrete outcome, acceptance criteria, scope, and links to prerequisite children. Put shared contracts or migrations before consumers. If a child cannot merge independently, combine it with its prerequisite or define a compatible intermediate state.
3. Present the proposed issue graph and unresolved product decisions. Stop for a decision if the plan does not establish a safe split or dependency order. Do not reinterpret approval of a plan as approval of an incompatible design.
4. Search existing children before mutation: a retry must reuse issues already created. GitHub permits at most 100 direct subissues per umbrella, including closed children. Count existing direct subissues and all missing links; if their total exceeds 100, stop for a plan split before creating or linking anything. Create one `☂️` umbrella only when none exists. Add or update a short checklist of children and note which can run in parallel. Create missing children with `gh issue create --parent <umbrella>` when supported. Link an existing child with `gh issue edit <umbrella> --add-sub-issue <child>`. On older `gh`, use `addSubIssue` with `GraphQL-Features: sub_issues`. Record actual issue numbers and dependency links in each child; a task-list mention alone is not a native subissue link. Confirm the parent reports every child as a subissue.
5. For an existing child, verify its issue and PR state before scheduling. An active owner or PR means in progress: adopt its PR into monitoring, do not assign another implementation worker, and obtain every risk-selected gate verdict from its worker or run fresh required gate subagents against that PR. If required revision-bound verdicts cannot be obtained, pause that child. Never create duplicate implementation workers for one issue.

## Dispatch and supervise

Use the runtime's available agent capacity, not a fixed three-worker cap. Count the coordinator, every issue worker and every nested gate against the same runtime budget; account for other consumers when the host exposes them. An explicit user concurrency limit remains binding. Report the effective budget and reservation before dispatch. Reserve at least one slot for selected nested gates: in a four-slot runtime, run at most two issue workers plus one gate. A reserved slot is available to ready gates, never to another issue worker. When no selected gate needs a subagent, no gate reservation is needed. If even one issue worker plus its required gate cannot fit, pause with the exact missing capability. Do not change host limits or permissions from the skill. Start every eligible child in its own fresh worker and worktree, from the repository's freshly fetched default branch. Give it a prompt under 2 KB containing only its child URL, repository, worktree, branch, dependency contracts and the path to [worker-rules.md](worker-rules.md); never repeat the rules or fork coordinator history. Persist its dispatch ID, then follow [worker-events.md](worker-events.md). Require fresh subagents for selected review and manual-test gates. The coordinator never authorizes another review cycle or fix pass: each worker's budget is its own checkpoint under the shared convergence policy, and a worker at the limit delivers with follow-up issues or reports its blocker.

Run this scheduling loop in every harness, including Codex:

1. Reconcile accepted events and dependency state. A dependent child becomes eligible only after every prerequisite PR is merged and its issue is closed. Dependency cycles and missing prerequisites block that child.
2. Grant capacity to ready review/test gates first, then launch eligible issue workers into every remaining unreserved slot. Dispatch the entire eligible batch before any blocking wait; spawning one issue and waiting for it while another issue fits is a scheduling failure. Independent workers continue while another worker waits for a gate or CI.
3. When no further authorized work fits, wait for the next event from any active dispatch under [worker-events.md](worker-events.md). Do not wait for all workers or finish one issue before servicing another. A worker may emit gate-capacity requests and releases without waiting for a coordinator question. A gate-capacity request is a scheduling event; grant one lease per free slot, otherwise queue it without treating temporary saturation as missing capability.
4. On a gate completion, accept its event, release its logical lease and close its execution when supported. Reclaim the host slot only when the host makes it reusable; then service the oldest ready gate before admitting another issue. On an issue completion, accept its result and reclaim its worker slot under the same host rule. Recompute eligibility and refill immediately. Never duplicate work or start optional hunts just to occupy a slot.

The coordinator owns the shared slot ledger and serializes lease grants; workers never independently assume a shared slot is free. When nested spawning is available, the issue worker uses its granted lease to launch the fresh gate and returns the lease with its terminal event. When the host cannot spawn grandchildren but can launch fresh gate contexts from the coordinator, the coordinator dispatches the worker's gate request and returns its verdict; implementation ownership stays with the issue worker. Do not create a gate-coordinator subagent that needs another slot to launch the actual reviewer. Each Code, Findings or tester execution consumes one lease, with no extra wrapper worker.

Use all free capacity for eligible issue workers and selected ready gates. Leave capacity idle only for a recorded gate reservation, dependencies, explicit user/resource limits, unavailable capability, or no remaining authorized independent work; record the reason at the scheduling event without polling. Completed open threads still consume capacity on runtimes that count them: close them when supported. If the host retains completed threads and exposes no way to release them, preserve the checkpoint and pause on exhaustion with the exact thread-release blocker. On runtimes that count active turns instead, use that accounting and do not invent a close tool. Never make the parent a spare implementation worker.

Track each child's issue, worker or existing owner, branch/worktree, prerequisites, risk selection, evidence or checkpoint gate verdicts, gated PR head SHA, PR, required review threads, merge state, and issue state. A message that code is done is progress, not completion. With evidence enabled, accept completion only when the child's evidence record is complete for the final PR head. With evidence disabled, require its checkpoint to record every selected gate as passed for that exact head. In both modes every selected hosted gate must pass, all required review threads must be resolved, the PR must be merged, and the issue must be closed. Compare the gated revision with the PR head SHA recorded immediately before merge, not the squash merge commit SHA. For an already merged child, collect the applicable revision-bound verdicts before releasing dependents; missing verdicts pause that child. Follow the repository's documented merge method for each PR. If a worker fails, preserve its issue/worktree and report the blocker. Resume from recorded GitHub and worker state rather than recreating issues or repeating finished work.

A worker sends exactly one final hand-back containing its checkpoint path and terminal result. Gate-capacity requests and releases are scheduling events; other interim status is sent only as a direct reply to a coordinator question. Host-required progress reports use the last meaningful event without waking the worker or reading status. Record an accepted terminal event before downstream work; duplicate or delayed completion events never dispatch another gate or delivery action. At 100,000 cumulative input tokens for that worker, it writes its checkpoint and hands off to a fresh worker for the same child; this fixed threshold applies in every harness and does not depend on optional telemetry. The coordinator never absorbs the implementation. Accept a merged child's recorded gate verdicts and never spawn new gates for it.

After every graph mutation, dispatch, worker update, gate result, PR change, CI result, review-thread change, merge or issue-state change, atomically update the matching child and the parent's `nextAction`. Mark the parent blocked with the exact child and recovery action when coordination cannot continue. Complete the parent checkpoint only after every child and the umbrella are verified closed; its outcome records the umbrella URL and the children's final PR heads and merge commits.

Workers inherit the original user authorization record and its scope, limits, consumed allowances and revocations from the checkpoint. The coordinator forwards verified authority; it never widens it. A replacement worker reads [authorization.md](authorization.md) and continues already authorized work without requesting the same permission. Internal limits trigger focused acceptance triage, not new optional hunts.

## Agent availability and pause

Check that a worker can launch before dispatch. In Sail, check that fresh review and manual-test subagents can launch before treating a worker as runnable. If any required agent tool or session is unavailable, pause the run and report the exact unavailable capability and affected issues. Do not implement a child in the parent, run either gate inline, or treat automated tests as a manual-test substitute. Resume only when the required agent is available; keep completed children recorded.

The review's Code and Findings Adversaries remain sequential. The manual-test adversary starts after a clean review. This gate ordering applies within each worker; independent workers may run concurrently up to the pool limit.

## Finish

After all children are verified complete, close the umbrella with a completion comment if GitHub has not closed it. Report its link, each child issue and PR, gate verdicts, CI, merge/closure status, and any remaining blocker. A partly merged umbrella is in progress, never complete.
